What I need from you before I change anything

Two things came out of the audit that should be fixed before a payment gateway is added, and four product decisions are genuinely yours to make. Everything else in this document is information.

D1
May I upgrade Next.js 16.2.10 → 16.3.8+ (and sharp 0.35.5)?
The installed Next.js carries 17 open security advisories including critical remote-code-execution ones. Most need conditions this site does not meet, but I will not build a payment webhook on a framework version with an unpatched middleware-bypass class of bug. This is the one dependency change I consider mandatory pre-work. It is also the riskiest change in the whole plan, so it gets its own deploy and its own test pass.
D2
Will you rotate the leaked GitHub token? (your action, on GitHub)
A personal access token is still sitting in plaintext in .git/config. I cannot fix this from here and I will not print the value. Revoke it at GitHub, then we replace the remote URL with the read-only deploy key the server already uses.
D3
Which security fixes should I implement now, before the gateway?
My recommendation is the four labelled do first below: login rate limiting, the CMS link-scheme check, the inquiry throttle, and the SVG upload handling. They are small, contained, and each one weakens the payment work if left undone.
D4
When an online checkout expires unpaid, should the held seats and stock be released?
Today an unpaid order holds its workshop seats until a human cancels it. With online payment a checkout expires automatically after 30 minutes. Releasing the seats then is more accurate but it is new behaviour that touches capacity. I lean toward releasing, on the checkout.expired event only, and never touching a paid or part-paid order.
D5
Should online card payment sit alongside "pay at the counter", or replace it?
The existing flow (customer orders, office records cash or a bank transfer by hand) must keep working for walk-in customers. I plan to offer card payment as an additional option on /order, with the manual settle path untouched.
D6
Are refunds in scope now, or later?
Payments.lk has a full refund API. I recommend leaving refunds out of the first build and doing them in the provider dashboard, so the first release has one money-moving path to get right. Say the word if you want a refund button in the admin from day one.

How money and stock are modelled

This matters for the gateway, because the schema was designed so that money is never a client-supplied number and never a single flag.

  • Product carries price (LKR), donationPerUnit, an optional capacity for services, and active.
  • Sale is a money-bearing row. unitPrice and donationAmount are snapshotted at creation, so later price edits never rewrite history. orderRef groups the lines of one order (a multi-line order is several rows sharing one reference).
  • Sale.status is pending | paid | cancelled and is the money column. It drives seat capacity, sold counts and the fund.
  • Sale.fulfillment is a separate column (confirmed | packed | dispatched | delivered, NULL means New). The codebase treats merging these two as a serious bug.
  • Payment records a physical receipt (cash, bank transfer). A sale's paid total is the sum of its payments, so split payments need no special case.
  • FundEntry is the public donation ledger, one row per contribution, with @@unique([channel, refId]) making double-counting impossible in the database.
  • Pack is a scannable unit: a physical pack (in_warehouse → dispatched → sold) or a workshop seat voucher (issued → redeemed).
  • CustomerLink / CustomerMessage are the SMS receipt system: an unguessable token per record, and an outbox written inside the same transaction as the money movement.

The customer journey today

  1. The customer browses / and /order, which read live data from GET /api/catalog.
  2. The form posts product ids and quantities to POST /api/orders. That route reads prices from the database, re-derives every figure, checks workshop capacity inside the transaction, and writes Sale rows at status: 'pending'.
  3. A pending order contributes nothing to the public fund and mints no vouchers. It does hold workshop seats.
  4. The customer is texted an acknowledgement and a receipt link (/r/<token>).
  5. The office records the money by hand in /admin/donations → Orders: POST /api/admin/orders/<ref>/settle with action: 'pay'. In one transaction it flips the lines to paid, writes the FundEntry rows, mints service vouchers, writes one Payment row, and queues the customer's "we received your payment" text.
  6. Fulfilment then moves by hand, or by the customer replying CONFIRM / CANCEL by SMS.

There is no payment gateway anywhere in the codebase. I searched for PayHere, Stripe, PayPal and Payments.lk references across src/, prisma/ and the config: zero matches. All money is offline, and next.config.ts even sends Permissions-Policy: payment=() site-wide.

Can this architecture support hosted checkout and public HTTPS webhooks?

Yes, and cleanly. The specific reasons:

  • The pending-order gate already exists. The design already separates "customer said they want this" from "money received", which is exactly the state machine a gateway needs. Payment becomes a second way to reach paid, not a new order model.
  • There is a working, well-built webhook pattern to copy. POST /api/sms/webhook verifies a signed JWT over the raw body before parsing anything, uses a constant-time comparison, rejects alg: none, and deduplicates on a unique event id. A payment webhook is the same shape with a different signature scheme.
  • HTTPS on a public hostname is already in place (Caddy, Let's Encrypt, port 443), which is what the provider requires for a production webhook endpoint.
  • Idempotency has a house pattern: a unique index doing the deduplication work, instead of every caller remembering to ask "have I done this already?".

The constraints to design around are SQLite's single-writer model, the rule that a unique index can never be added to an existing table on this deploy path, and the fact that money fields must stay server-derived.

Phase 2

Security findings

Ordered by what an attacker gains, not by how easy the fix is. Every finding below is from reading the code; where a claim depends on a version or an advisory, I say so. I have deliberately not listed anything I could not point at in the source.

Headline. There is no critical vulnerability in the application's own code. The money paths are unusually careful: prices, totals, donations and payment status are all derived server-side, the donation ledger cannot double-count, vouchers are minted inside the payment transaction, and the existing webhook verifies its signature before reading a byte of body. The real risks are a dependency that needs upgrading, one unprotected login, one leaked token, and a small number of hardening gaps that matter more once card payments exist.

Details

F01

Admin login: no rate limit, no lockout, weak floor

High do first

src/app/api/auth/login/route.ts:4-12 · src/lib/admin-auth.ts:144-163

One shared password guards every admin API: orders, settle, donations, packs, messages, uploads. The login handler validates nothing else and counts nothing. 

export async function POST(request: Request) {
  const { password } = await request.json()
  const valid = await checkPassword(password)
  if (valid) { await setAdminCookie(); return NextResponse.json({ success: true }) }
  return NextResponse.json({ error: 'Invalid password' }, { status: 401 })
}

checkPassword accepts anything of length 4 or more. bcrypt at cost 12 slows each attempt to roughly 250 ms, which is real but not decisive: no lockout means an attacker can grind indefinitely and the attempt rate is bounded only by the CPU.

Impact
Full administrative takeover: read every order and customer phone number, mark orders paid, mint vouchers, change the password. This is the single highest-value target in the system.
Fix
Per-IP throttle plus a global bucket on the login route, using the existing createThrottle helper, and an escalating delay after repeated failures for the same IP. Raise the minimum to 10 characters and require it to be changed if the stored hash matches a known-weak value. Keep the response body as it is: it already leaks nothing.
Regression test
Twelve wrong passwords in a row from one IP: the first ten answer 401, the remainder answer 429, and a correct password from a fresh key still succeeds. Assert the global bucket also trips.

F03

GitHub token in plaintext in .git/config

High your action

.git/config → remote.origin.url · credential.helper = store

The push remote embeds a personal access token in the URL. It is not tracked by git, but it lives in plaintext on disk, is copied by any clone or archive that includes .git, and was previously printed verbatim into a terminal session. credential.helper = store means the same or a related token may also be sitting in %USERPROFILE%\.git-credentials.

Impact
Anyone with read access to this machine, or to a copy of the repository folder, gets push access to the private server repository. From there, code that runs as the site.
Fix
Revoke the token at GitHub (Settings → Developer settings → Tokens). Set the remote to the plain HTTPS URL and rely on the read-only deploy key the server already uses for pulls. Clear the stored credential. I will not print the value, and I have not.
Regression test
git config --get remote.origin.url shows no credentials, and git ls-remote still works.
F04

CMS links accept javascript: URLs

Medium do first

src/components/site/contact.tsx:105-114 · src/components/site/navbar.tsx:79,148 · written at src/app/api/content/route.ts:29-34

{content.socials.map((s) => (
  <a key={s.id} href={s.url} target="_blank" rel="noopener noreferrer">

The content endpoint stores whatever the admin editor sends after checking only that a brand key exists. React escapes the attribute value, so there is no quotation-mark breakout, but React does not block a javascript: scheme. A stored value of javascript:<payload> executes for any visitor who clicks that footer or navbar link.

Impact
Escalation from "can edit the website" to "runs script for every visitor". Practical here chiefly as a weapon after an admin session is stolen, which is precisely the scenario F01 describes.
Fix
Validate URL fields in the content schema: allow only http:, https:, mailto: and tel:, and reject anything else at save time. Render-time filtering as a second layer for already-stored values.
Regression test
POST content with socials[0].url = "javascript:alert(1)" → 400. A legitimate https:// value still saves, and the footer renders it.
F05

The public contact form is unthrottled

Medium do first

src/app/api/inquiries/route.ts:20-39

The route is public by design and validates field lengths, but calls no throttle at all. Every valid post is a database row.

Impact
Unbounded row growth in the one database the whole site shares, and flooding of the admin inbox so genuine enquiries are hard to find. Field lengths are bounded, so a single row is small.
Fix
The same createThrottle treatment the order form already has: a per-IP limit plus a global backstop. Consider a honeypot field, matching the order route.
Regression test

F06

Uploads accept SVG and trust the declared type

Medium do first

src/app/api/upload/route.ts:7-19,43-62 · served by Caddy per Caddyfile.production:12-15

The allow-list includes image/svg+xml and .svg, and validation trusts file.type and the extension from the filename. There is no magic-byte check. The write path is safe: the stored filename is server-generated from a timestamp and random suffix, so traversal is not possible. The delete path is also safe: it runs path.basename() first.

The gap is what happens after storage. Uploads are served by Caddy directly at /uploads/*, which means they bypass the X-Content-Type-Options: nosniff header set in next.config.ts. An SVG is active XML, so a script inside one runs in the site's origin when the file is opened directly.

Impact
Persistent script on the public origin, plantable by anyone holding an admin session. Bounded by the admin-only gate, which is why this is Medium and not High.
Fix
Simplest: drop SVG from the allow-list; the farm's imagery is raster. If SVG is genuinely wanted, add magic-byte sniffing and serve /uploads/* with nosniff plus Content-Disposition: attachment for SVG from Caddy.
Regression test
Upload a file whose bytes begin <svg but whose declared type is image/png: expects 400. A genuine JPEG still uploads.

F08

The /admin page guard validates presence, not validity

Medium

src/middleware.ts:19-30

const session = request.cookies.get('admin_session')
if (!session?.value || session.value.length < 20) {
  return NextResponse.redirect(loginUrl)
}

Middleware never checks the token against the database. A forged cookie of 20+ characters gets the /admin shell rendered. This was measured on 2026-10-04 through a public tunnel: /admin/orders returned 200 with a forged cookie.

The impact is genuinely small right now, and this is worth stating precisely because it is easy to overstate. Every admin page is a client component that fetches its data through API routes, and I verified that all 31 admin route files call isAdminAuthenticated() as their first statement, comparing the token against the database. A forged cookie yields an empty interface and 401s. No password hash is read back by any endpoint, and no page imports Prisma directly.

Impact
Exposure of the admin interface's existence and layout to unauthenticated visitors. No data, no actions.
Fix
Have the admin layout validate the session server-side and redirect, so the shell is never rendered without a real session. Keep the API checks as the actual enforcement.
Regression test
A forged 96-character cookie on /admin/orders → redirect to login. A real session still renders the page.

F11

Duplicate payment and voucher writes rest on an application check

Low relevant to Phase 6

src/app/api/admin/orders/[orderRef]/settle/route.ts:43-161 · prisma/schema.prisma:252-270

Settlement reads pending lines, then updates them. The donation ledger and the customer messages are protected by unique indexes, so they genuinely cannot double-count. Payment and the service vouchers have no such constraint: a pair of truly concurrent requests that both read status: 'pending' could in theory each create a receipt and a voucher set. In practice SQLite's write lock makes the loser fail, and the sequential case is caught by the re-check.

Impact
Two receipt rows and two sets of vouchers for one order, in a narrow race. The money figure itself never changes, because the fund ledger is constraint-protected.
Fix
This is where the gateway work changes the picture: a webhook can legitimately arrive twice, so I will add a dedicated payment-intent table with a unique key and route both the webhook and the manual settle through one transactional function. Do not add a unique index to the existing Payment table: on this deploy path, prisma db push aborts the deploy rather than prompting.
Regression test
Fire two settle calls concurrently against a database copy: exactly one Payment row and one voucher set exist afterwards.
F12

Low

The verified API contract

Base URLhttps://api.payments.lk. There is no separate sandbox host: the key decides the mode.
AuthAuthorization: Bearer sk_test_… or sk_live_…, server-side only. Publishable keys may only create checkouts and cannot be called cross-origin, so the browser is not a viable path.
Create checkoutPOST /v1/checkouts. Requires an Idempotency-Key header.
BodyExactly one of: amountCents + description, or lineItems. Plus optional reference (max 64), customer, successUrl, cancelUrl, locale, saveCard.
Amount formatInteger cents of LKR. The spec's own words: "The amount in LKR cents, from Rs. 10 (1000) to Rs. 1,000,000 (100000000)… Take it from your own records, never from the browser." There is no currency field to send. A fractional number is refused, never rounded.
Response201 with the checkout object: id (chk_…), status, url, expiresAt, and a nested payment object. The checkout expires 30 minutes after creation.
RedirectSend the browser to the returned url. The spec on successUrl: "It proves nothing; confirm from the webhook."

Signaturet=<unix seconds>,v1=<hex HMAC-SHA256 of "<t>.<raw body>"> under the endpoint's whsec_ secret. Refuse if t is more than 300 seconds from your clock. Verify before parsing the JSON. During a secret rotation the header carries one v1 per secret, newest last; accept a delivery if any matches.

RefundsPOST /v1/refunds exists (needs an Idempotency-Key, live refunds leave from the next bank working day). Not dashboard-only.
SandboxTest cards with the outcome decided by the expiry date: 01/39 approved, 05/39 declined, 04/27 expired card. CVV 100. Sandbox checkouts only work once the account application has been submitted.

Two contract details that shape the design

  • The browser return carries nothing we can trust. The documentation does not define query parameters appended to successUrl/cancelUrl, and it states plainly that the return proves nothing. So the server must store checkout.id against our order at creation time, and settle only from the webhook or from a server-side lookup.
  • The minimum is Rs. 10. An order whose total is below that cannot be paid by card. The catalog currently holds three items and prices are set by the owner, so this needs an explicit rule rather than an assumption.

Required flow

sequenceDiagram
    autonumber
    participant C as Customer
    participant S as Our server
    participant P as Payments.lk
    C->>S: place order, items only
    S->>S: derive prices, check seats, write pending order
    S->>P: create checkout with server key
    P-->>S: checkout id and hosted page url
    S-->>C: redirect to the hosted page
    C->>P: pays on the provider page
    P-->>C: browser returns to our status page
    P->>S: signed webhook to our endpoint
    S->>S: verify signature over the raw body first
    S->>S: check type, mode, amount, currency, order
    S->>S: settle in one transaction
    S-->>P: 200 OK

The important property: the customer's browser and the webhook travel separately, and only the second one can move money. The return page reads its own order status from our database and shows the truth, which at that instant is usually still "pending, confirming". That is a slightly less satisfying page than a green tick, and it is the correct one.

SDK or hand-rolled?

The provider maintains @payments-lk/node at 0.4.1 and documents a Node server as the supported path. There is no Next.js-specific SDK. My recommendation is to not install the SDK for the webhook, and to use plain fetch plus node:crypto for the checkout call, for three reasons specific to this project:

  • The webhook verification is about twenty lines and this codebase already contains a hand-rolled verifier of exactly that shape, reviewed and tested. A second, subtly different verification path is a worse outcome than one shared one.
  • The whole point of the existing design is that money-touching code has one writer. Wrapping the settle function behind an SDK's event object does not improve that.
  • This project has deliberately pruned dependencies, and a payment SDK would add a transitive tree to a farm website. That is a real trade, not a purity argument, and it becomes worth taking if the SDK's typed events would replace hand-written parsing we would otherwise have to maintain.

If you would rather use the official SDK, that is a reasonable call and I will follow it; I would still verify the signature ourselves and use the SDK only for typing. Your decision, flagged as D7 in the next section.

3. Schema: two new tables, and why not a third

model PaymentIntent {
  id            String   @id @default(cuid())
  orderRef      String   @unique   // one open intent per order
  checkoutId    String?  @unique   // chk_… from the provider
  paymentId     String?  @unique   // pay_… from the webhook
  mode          String             // 'test' | 'live'
  amountCents   Int                // the server-derived figure we asked for
  status        String   @default("open")
  //              'open' | 'succeeded' | 'failed' | 'expired' | 'cancelled'
  checkoutUrl   String?
  expiresAt     DateTime?
  failureMessage String?
  feeCents      Int?               // the provider's fee, for reconciliation
  netCents      Int?
  cardScheme    String?            // 'VISA' — never a card number
  cardLast4     String?
  createdAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt
}

model PaymentWebhookEvent {
  id          String   @id @default(cuid())
  eventId     String   @unique   // the provider's evt_… id
  eventType   String
  mode        String
  orderRef    String?
  rawPayload  String
  processedAt DateTime?
  note        String?
  createdAt   DateTime @default(now())
  @@index([createdAt])
}

Both are new tables, which matters concretely: a unique index on a new table is created as part of CREATE TABLE and is free, while adding one to an existing table makes prisma db push abort under the deploy script's data-loss gate. This is why the intent lives in its own table rather than as columns plus a unique key on Payment. The alternative of putting providerRef on Sale was rejected for the same reason, and also because it would tempt the money column and the gateway state to drift into each other.

4. Migration and rollback

  • Forward: npx prisma db push creates two tables. No existing table is redefined, no column is added to an existing table, no data is touched. Dry-run on a copy of the live database on the VPS first, exactly as the existing deploy discipline requires.
  • Feature off by default: with no PAYMENTS_LK_SECRET_KEY set, the start route returns "card payment unavailable" and the order flow behaves exactly as it does today. The upgrade is inert until the keys are added.
  • Rollback: unset the environment variables, redeploy the previous commit. The two tables can stay; they are additive and nothing reads them. There is no data-loss step and no schema reversal needed.
  • Hard constraint to respect: never add a unique constraint or a foreign key to an existing table in this schema. The repo's own comments record that this aborts the deploy.

8. Deployment risks

  • Production is behind the repository. The pre-SMS build was measured live on 2026-10-04. The payment work depends on that undeployed code. Deploy and verify current main first.
  • The Next.js upgrade is the riskiest single change and is why it gets its own deploy cycle. It is a major-adjacent version bump on a client-heavy App Router site.
  • SQLite is a single writer. A webhook and an admin action arriving together is exactly the concurrency the design has to absorb. The transaction plus unique index pattern handles it; it must be tested, not assumed.
  • The webhook must answer within 10 seconds. The settle path sends SMS after the commit, never inside it, which is already the house rule and is now also a delivery requirement.
  • Silent failure is the real danger. If the webhook is misconfigured, payments succeed at the provider and orders stay pending here. The reconciliation action and the stuck-intent list exist for that, and both need to be visible in the admin rather than buried.
  • A tunnel is not an option for the webhook. It needs the real HTTPS domain, which already exists. No new exposure is required for this, which is a genuine advantage of the current setup.

Appendix

Method, limitations and reassurance

How findings were established

Phase 1 and 2 are a static trace: reading the route handlers, the shared libraries, the Prisma schema, the middleware, the deploy script and the Caddy configuration, and running tsc, lint, npm audit and read-only database queries. The payment contract was verified against the provider's published OpenAPI document rather than against documentation prose alone. Two claims come from measurements recorded in this project's own history rather than from my session: the forged-cookie result on /admin/orders, and the fact that production is running the pre-SMS build. Both are cited as history, not re-tested.

What I deliberately did not do

  • No file in the repository was modified. The only thing written was this report, in a gitignored scratch directory.
  • No production data was read, downloaded or copied. The local database was queried for table names and row counts only.
  • No intrusive scan was run against the live site, and no third-party system was tested.
  • No secret value was printed. Where a secret exists, this report names the file and the variable.
  • No live payment, refund or credential change was made. No account was created at the provider.
  • The E2E suites were not executed, because they mutate a database copy and start a server. They are the acceptance gate for the fix work, not for this read-only pass.

The honest summary

This is a small, unusually careful codebase. The parts that handle money were written with the specific failure modes of an e-commerce site in mind, and several of them are better than what you would find in a typical shop of this size: server-derived pricing, a constraint-protected donation ledger, vouchers minted inside the payment transaction, and a webhook that verifies its signature before parsing anything. I did not find a way for an unauthenticated stranger to change a price, mark an order paid, or read another customer's order.

What it does not yet have is a hardened perimeter: the single shared admin password has no lockout, the framework is a version behind its security patches, a token is sitting in plaintext on the dev machine, and a few public endpoints are cheaper to abuse than they should be. None of those is exotic and all of them have small, surgical fixes. They are worth doing before a card gateway, because a gateway makes the admin account worth more to an attacker, and because it adds a new way for money to move that must be the most carefully tested code in the project.

I have not started any of it. Approve D1 to D6 and I will begin with Phase 5.
